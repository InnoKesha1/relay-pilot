# Развёртывание пилота

Скрипты рассчитаны на **новые выделенные под пилот** VPS Debian 12 / Ubuntu 24.04 x86-64 с systemd. Развёртывание на реальных VPS ещё не выполнено. Нужны три IPv4, SSH-доступ владельца и домен. Все примеры `example.com`/`192.0.2.*` нужно заменить. В опубликованных файлах нет рабочих ключей.

## Размещение и порты

| Узел | Входящие порты | Процессы |
|---|---|---|
| A | TCP 443; SSH только владельцу/контроллеру | sing-box Reality |
| B | UDP 443; TCP 80/443 для сертификатов; ограниченный SSH | sing-box Hysteria2, Caddy |
| Выход | TCP 8443 **только с IP входов A/B**; TCP 80/443; ограниченный SSH | sing-box VLESS TLS, Caddy, Go/SQLite |

Порты 8090 и `/metrics` доступны только на loopback выхода. Настройте эти правила в сетевом экране каждого провайдера до выдачи доступа. На входах правила sing-box дополнительно разрешают пользовательские подключения только к IP выхода и его порту. Выход запрещает обращения к приватным адресам. Для узлов используйте разные IP; входы должны быть у разных провайдеров.

Укажите DNS A-записи `sub`, `exit`, `reality` на выход, `b` на вход B. Записи AAAA добавляйте только после настройки и проверки IPv6. Reality использует **собственный** HTTPS-ресурс `reality.example.com`; контрольный сайт МИРЭА не участвует в туннеле.

## Установка

1. Скопируйте каталог `ops/` на три узла. Выполните `sudo bash ops/install-node.sh`. Скрипт проверяет SHA-256 sing-box 1.13.0, устанавливает helper и systemd guard. Без действующей конфигурации транспорт не запускается.
2. На B и выходе выполните `sudo bash ops/install-caddy.sh`. Это закреплённый Caddy 2.10.2. Подготовьте `/etc/caddy/Caddyfile` по `ops/Caddyfile.example`: на B только имя `b`, на выходе остальные три. Сохраните глобальный блок отключения HTTP/3 и журналов запросов.
3. Выполните `sudo caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile`, затем `sudo systemctl reload caddy`. Дождитесь выпуска публичных сертификатов. Для Reality нужен работающий TLS 1.3 на собственном `reality`-домене.
4. На B и выходе установите `copy-certificate.py` как `/usr/local/sbin/relaypilot-copy-certificate` с правами 755. Запишите `/etc/relaypilot/certificate.env`: на B `CERT_DOMAIN=b.example.com`, на выходе `CERT_DOMAIN=exit.example.com`. Установите `relaypilot-cert.service` и `.timer` в `/etc/systemd/system`, выполните `systemctl daemon-reload`, `systemctl start relaypilot-cert.service`, `systemctl enable --now relaypilot-cert.timer`. Helper копирует сертификаты из стандартного хранилища пакета Caddy и обновляет транспорт после продления.
5. Соберите сервер: `cd service && go build -trimpath -o ../dist/relaypilot-linux-amd64 ./cmd/relaypilot` на Linux amd64 либо используйте артефакт Actions. На выходе выполните `sudo bash ops/install-control.sh /absolute/path/relaypilot-linux-amd64`.
6. На выходе создайте отдельный SSH-ключ контроллера: `sudo -u relaypilot ssh-keygen -t ed25519 -N '' -f /etc/relaypilot/ssh/id_ed25519`. Установите **публичную** часть в `~relaydeploy/.ssh/authorized_keys` всех трёх узлов с префиксом `restrict,from="IP_ВЫХОДА"`. Каталог 700, файл 600, владелец relaydeploy. Это отдельный ключ только для пилота.
7. Сверьте отпечатки SSH host keys через консоль провайдеров и заполните `/etc/relaypilot/ssh/known_hosts`. Автоматического принятия неизвестных ключей нет. Контроллер должен иметь возможность SSH-подключения также к выходу.
8. Сгенерируйте Reality-пару: `sing-box generate reality-keypair`, короткий ID: `openssl rand -hex 8`. Скопируйте `ops/inventory.example.json` в `/etc/relaypilot/inventory.json`, заполните IP, домены, ключи, SSH. Приватный ключ Reality нужен только контроллеру и входу A. Файл 600, владелец relaypilot. Папка `/etc/relaypilot` должна разрешать чтение владельцу контроллера.
9. Выполните `sudo -u relaypilot relaypilot sync`. Helper на каждом узле проверит конфигурацию, установит её атомарно и подтвердит запуск. Затем `sudo systemctl start relaypilot-control`. Проверка: `curl --fail https://sub.example.com/healthz` должна вернуть HTTP 204.

## Управление доступом

Команды выполняются на выходе. Срок задаётся явно в RFC3339; UTC заканчивается на `Z`.

```sh
sudo -u relaypilot relaypilot user add owner 2026-10-06T00:00:00Z
sudo -u relaypilot relaypilot user list
sudo -u relaypilot relaypilot user expire USER_ID 2026-11-06T00:00:00Z
sudo -u relaypilot relaypilot user rotate USER_ID
sudo -u relaypilot relaypilot user revoke USER_ID
sudo -u relaypilot relaypilot sync
```

Добавление/перевыпуск выводят персональную ссылку **один раз**. База хранит её хеш; утраченный токен нельзя восстановить, его перевыпускают. Не вставляйте ссылки в общий чат, задачи GitHub, мониторинг и shell-команды. `rotate` меняет также все транспортные учётные данные; старый закешированный профиль перестаёт работать после применения на узлах. Отозванный участник не возобновляется продлением: создайте новый доступ. Лимит — 10 активных участников.

Для QR используйте локальный `tool/subscription_qr.dart` по инструкции BUILD: вход — файл со ссылкой, выход — секретное PNG. В Windows приложение читает QR из файла, в Android также камерой. Изображение требует такой же защиты, как ссылка.

## Синхронизация и отказ

CLI сохраняет изменение в SQLite и применяет его на всех трёх узлах. Ошибка хотя бы одного узла возвращает ненулевой код и сообщение о незавершённой доставке. Демон повторяет синхронизацию каждые 15 секунд. Серверы получают только актуальных участников.

Снимки базы имеют возрастающий номер. Helper отвергает запоздалый снимок, поэтому параллельный старый запрос не восстанавливает отозванный ключ. Разрешение работы узла ограничено 60 секундами и ближайшим сроком истечения участника. Guard проверяет его каждые 10 секунд: при потере контроллера узел останавливается, обычно в пределах 75 секунд от последнего снимка. Нужны синхронизированные часы/NTP. Это сознательный выбор пилота в пользу отзыва доступа; недоступность управления может остановить ещё работающий транспорт.

Изменение состава участников перезапускает sing-box и разрывает существующие подключения. Обычная синхронизация неизменной конфигурации обновляет только разрешение. Ошибка проверки сохраняет действующую конфигурацию; ошибка запуска новой конфигурации останавливает узел. Автоматический возврат старых ключей запрещён.

## Резервная копия и откат

`relaypilot-backup.timer` создаёт ежедневный согласованный снимок SQLite через `VACUUM INTO`; учитывается WAL. Ручная копия: `sudo -u relaypilot relaypilot backup /var/lib/relaypilot/backups/manual-UNIQUE.db`. Существующие файлы не перезаписываются. Сохраняйте зашифрованную копию вне общего выхода, вместе с inventory, SSH и ключом подписи APK. База содержит транспортные секреты. Настройку внешнего хранилища выполняет владелец; она не включена в VPS-смету.

Откат приложения/бинарника: сохраните актуальную БД, установите предыдущий проверенный бинарник и снова выполните `relaypilot sync` из **текущей** базы. Не применяйте `node/previous.json`: он может содержать отозванные ключи.

Восстановление БД после аварии проводится при остановленном контроллере и транспорте на всех узлах. Скопируйте backup в отдельный staging-файл; проверьте `PRAGMA integrity_check;`, выполните в staging `UPDATE users SET revoked=1;`. Сохраните текущую БД и её WAL, затем замените основной файл staging-копией при закрытых процессах. Владельцем остаётся relaypilot, права 600. После запуска выдайте новые доступы подтверждённым участникам. Такой порядок не возобновляет доступ из устаревшей копии. Не удаляйте WAL работающей базы.

## Наблюдение

`systemctl is-active relaypilot-node relaypilot-guard.timer`, `systemctl status relaypilot-control`, `curl http://127.0.0.1:8090/metrics` и публичный `/healthz`. Метрики содержат время успешной синхронизации и количество ошибок, без URL участников, IP клиентов и истории сайтов. Ошибки синхронизации пишутся обезличенно; sing-box не пишет журнал трафика. Проверка `/healthz` подтверждает работу управления и недавнее применение конфигов, а не полную цепочку пользователя — её проверяет клиент каждые 15 секунд.
